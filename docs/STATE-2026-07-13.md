## The wire — GSTA state + ZCS2 envelope
Two things ride one WebSocket:
- **ZCS2** = the streaming-zstd video wire (magic `ZCST`, streaming zstd context, periodic reset). This is what carries the TA (stage + effects + HUD) and VRAM page diffs. Prod flags: `MAPLECAST_ZSTREAM=1 ZSTREAM_LEVEL=3 ZSTREAM_SOA=1 ZSTREAM_RESET=600` (+ `TACANON=1`, `PAGEGATE=1`). **Note: prod uses zstd level 3, not 9** — a deliberate latency cut (B3, 0.313→0.065 ms/frame compress). *(The OVH/local run scripts currently use level 9 — should be dropped to 3 to match; minor.)*
- **GSTA / STM2** = the per-frame **game state** (char pos/anim/sprite_id + the body render-deposited state) folded onto the *same* wire as a trailing **STM2** section (`STATE_MERGE=1`). One socket, same vframe, no pairing drift. The client draws character bodies from this — **SH4 OFF**.
- Bandwidth: **~3 Mbps** gameplay, **~6 Mbps** triple-super spike (the super render-state is a genuine render_frame floor).

## Render architecture (the shipping checkpoint)
- **Stage + effects** → ride the ZCS2 wire pixel-perfect. Static stage ≈ free (zstd dedup). `STAGESTRIP=0`.
- **Character bodies** → server **strips** the body quads (`CHARSTRIP=1`); the client draws them **locally via `render_frame`** (the transpiled-SH4 render, byte-exact) from the folded STM2 body state. `bodytex=local` (client decodes texels from cache).
- `VCACHE=1` (content-addressed VRAM page cache), `NO_SCENE_SYNC=1`.
- **Default client**: `web/webgpu-test.html` — pure-JS WebGPU renderer + `render_frame.wasm` (bodies) + `fzstd` (decompress). Client defaults: `statemerge`+`fxdecode` ON, `bodysrc=wasm`.

## A2 run-ahead — the big work (DONE)
**Goal**: publish frame N+1's render at N's wall-clock time to hide MVC2's measured 1-frame internal lag → visible reaction ~39 ms → ~22 ms.

- **3-leg cycle** (`core/emulator.cpp` ~1758-1815): leg1 hidden→N (+save); leg2 lookahead→N+1 (builds N+1's list); leg3 publish→N+2 (MVC2's deferred submit fires N+1's render, captured + shipped); rewind→N. Verified **+1 offset** on the state wire.
- **Crash fixed** (`9184dc3ae`): viewer forced-SYNC raced `FinishRender` on the single `rqueue`; fix = `rend_wait_render_idle()` barrier. Gate: 20 request_syncs → 0 crashes.
- **dirty-page rewind** (`62c53017f`): rewind restores only the ~137 changed pages (~550 KB) instead of a full 28 MB `dc_deserialize`. **12.9 ms → 1.9 ms** on the 5900XT. Audit proved memwatch tracking is complete (LEAK=0 all regions). **Determinism gate: 0 diffs / 1800+ rewinds** (byte-identical to the full path). Gated `MAPLECAST_RA_DIRTY_REWIND`.
- **short-leg-3** (`99f0cfb1b`): the step-stop is at VBLANK, so leg3 ran a full frame after publishing; short-leg3 halts it the instant N+1 ships (skips the rewound N+2 tail). **preview 4.1 → 2.0 ms.** All 3 gates green (+1 offset, determinism, fps). Gated `MAPLECAST_RA_SHORT_LEG3`.
- **spike logger** (`ea7a36d0d`): `MAPLECAST_RA_SPIKE=1` flags any tick > 16.67 ms (a visible dip).
- **KEY REFRAME**: the dirty-page rewind is 1.9 ms on the **non-X3D** 5900XT — *faster* than the AX102's X3D (2.5 ms). The tiny working set killed the V-cache advantage. So **X3D is no longer required**; a fast desktop-Ryzen dedicated (no browser contention) is all it takes.

## The honest latency conclusion
Run-ahead **works** (server-side proven: 5.5 ms tick, +1 offset, ~0 spikes). But its **16.7 ms is one frame**, and how much it's *felt* depends on the total:
- **Local / LAN (~0 ms)**: 16.7 ms is a big fraction of a ~30 ms E2E → **feels clearly snapper** (confirmed on the 5900XT locally).
- **Over the internet (~20-40 ms + render + vsync ≈ 80-120 ms E2E)**: 16.7 ms is ~15%, and **SSH-tunnel jitter (TCP-over-SSH) masks it**. Real competitive edge, not a dramatic transform. This matched the user's read on the OVH tunnel test.

So server run-ahead is a **competitive-margin edge for browser clients**, best over low-latency links. The **dramatic** low-latency win is client-side prediction (below).

## Next direction — native client (Tauri / Dioxus) + local prediction
The current client is the browser (`webgpu-test.html`): WebGPU render + WS wire + **WS input**. Browser costs: WS input latency, rAF/vsync beat, no native UDP.

A **Tauri** (Rust + system webview) or **Dioxus** (Rust-native UI) desktop app, in rising order of latency win + effort:
1. **Wrap the web client** (Tauri webview loads the existing page) — a real native app; quickest. Same render/wire latency as the browser, but you can add a **native UDP input path** (Rust → `:7100` sendto) instead of the browser WS — the cheapest, biggest single latency cut on the input side.
2. **Native render** (Dioxus + `wgpu`, port the render client to Rust) — drops all browser-engine overhead; bigger effort.
3. **Local prediction — the endgame** (`ROLLBACK-PREDICTION.md`): the desktop app runs its **own SH4** (native flycast core via FFI, or a full-SH4 WASM) and predicts the next frame **on the player's machine** (near-zero latency), validated against the server's authoritative input log. This is where latency actually collapses — the frame isn't shipped, it's computed locally. Server run-ahead becomes moot for native players.

**Recommendation**: start with a Tauri wrapper + **native UDP input** (biggest cheap win), then evolve toward local prediction (3). This is the competitive-client vision made concrete.

WASM builds that exist today: `packages/renderer` → the browser renderer (TA parser + WebGPU, **no SH4**, 831 KB); `render_frame.wasm` → transpiled SH4 body render. Neither runs the game logic — option 3 needs the native flycast core (headless build already exists) embedded via FFI, or a new full-SH4 WASM.

## Open items / gotchas
- **OVH `run_ra.sh` uses `ZSTREAM_LEVEL=9`; prod uses 3** (faster compress). Drop OVH to 3 to match — minor latency.
- **Make `MAPLECAST_RA_DIRTY_REWIND` + `MAPLECAST_RA_SHORT_LEG3` default** (both gate-proven) before any prod arming.
- **Prod run-ahead still OFF** by design. Arm = add `MAPLECAST_RUNAHEAD=1` (+ the two flags) to `/etc/maplecast/headless.env` + restart; disarm = remove + restart.
- **`MAPLECAST=1` is the input gate** — without it join+render work but ALL input is silently dropped (see DEPLOYMENT.md checklist). The one that cost hours.
- **Direct-by-IP over HTTP breaks WebGPU** (needs a secure context: HTTPS or localhost). A public OVH endpoint needs caddy + a real cert (Let's Encrypt on a `nobd.net` subdomain, grey-cloud DNS → direct, no Cloudflare hop).
- Diagnostic env flags (all default-off, committed): `MAPLECAST_STATEVF`, `MAPLECAST_DESER_PROF`, `MAPLECAST_RA_REWIND_AUDIT`, `MAPLECAST_RA_DIRTY_GATE`, `MAPLECAST_RA_SPIKE`, `MAPLECAST_RUNAHEAD_TRACE`.
